# 오탐 데이터 수집 결과 (2026-11-26)

트리아지가 "오탐을 가려내는지" 보려면 정상 트래픽에서 실제로 울린 알럿이 필요하다. 내 랩·레포 전체를 훑어 찾은 것만 모았다.
**결론부터: 실제 규칙 알럿 오탐은 2건뿐이다.** 정상 트래픽 오탐률을 따로 잰 적이 거의 없었기 때문이다(`api-security-supply-chain/automate/rules/wazuh_rules_v2/README.md`에도 "정상 트래픽 오탐률은 아직 못 쟀다"고 적혀 있다).

## 이 데이터가 증명하지 못하는 것

- 규칙 오탐 2건은 **같은 원인(FastAPI가 자동으로 여는 문서 화면)**이다. 이 오탐은 코퍼스의 `0915`에 **예외 4개를 손으로 추가해서 이미 고쳤다**. 즉 지금 룰로 같은 로그를 넣으면 안 울린다. 트리아지 평가에 쓰면 "고치기 전 룰의 알럿"을 평가하는 셈이고, 코드가 쓰는 예외 목록과 같은 출처라서 **순환 평가**(레포 README의 12/12)와 같은 문제를 갖는다.
- 규칙 오탐의 다양성이 없다. 다른 유형의 정상 트래픽(예: 새 정상 엔드포인트가 명세에 없는 경우, 로그인 재시도, 크롤러)은 데이터가 없다.
- ML 이벤트 48건은 `rule` 필드가 없어서 현재 `rag/triage.py`(룰 ID로 정의를 조회)에 **그대로 넣을 수 없다.** ML용 사실 계산(점수, 창 요청 수, 허용 목록)이 따로 필요하다.
- 라벨은 이 랩의 생성기·문서가 정한 것이다. 사람이 하나씩 검토한 정답이 아니다.

## 더 모으려면 (아직 안 한 것)

1. **실제 Wazuh로 확인한다.** 로컬에 `wazuh-manager` 이미지가 없어(1.5GB 이상, C: 여유 확인 필요) 팀 로그는 룰을 파이썬으로 재현한 도구로 돌렸다(`docs/fp_team_logs.md`, DVRA 450줄에서 실제 logtest와 일치 확인). 이미지를 받으면 같은 로그로 실제 logtest를 돌려 재현 결과와 대조할 수 있다.
2. ~~팀 웹 원본 로그는 다른 PC·VM에만 있다~~ → **로컬 `D:\team_raw_extract`에 백업돼 있어 분석했다**(108만 줄, 정상 6개 출발지 경보 34건 = 0.18%). 단 정상이 생성기 트래픽이고 라벨 4개가 "추정"이라 사람 정상 트래픽의 오탐률은 아니다.
3. 룰 v1(`100904`)이 정상 `/users/1`, `/users/15`, `/users/200` 한 건에도 level 12로 울렸다는 기록이 `0911` 머리 주석에 있다. 알럿 원문이 남아 있지 않아 수집하지 못했다.

**읽는 법**
- **오탐의 출처는 룰이 아니라 ML이다.** 앞서 모은 규칙 오탐(`/docs`, 팀 로그)은 많아야 수십 건인데 ML 오탐은 111명이다. 그래서 어댑터 우선순위가 달라진다 — 방어연습장 어댑터는 ML 이벤트(점수, 창 요청 수, 허용 목록)를 설명할 수 있어야 의미가 있다.
- 실행마다 목적이 달랐다(레이트리밋 실험 A~E, 허니 API, 기본 채점). 7개 실행의 정상 행위자 비율이 6/20~20/20으로 크게 다르다. **독립 표본이 아니고** 같은 생성기·같은 페르소나에서 나왔다.
- 연습장 설계 문서(`docs/benchmark-design.md`)가 스스로 적은 약점이 그대로 적용된다: **공격자 IP 대역이 고정**(정상 10.10 · 탐색 10.66 · BOLA 10.77), 탐색 경로·BOLA 순서 고정. 점수는 "이 생성기 기준"이다.
- 행위자(출발지 하나의 행동 묶음) 단위라 알림 한 건 한 건의 JSON이 아니다. 트리아지 입력으로 쓰려면 ML 이벤트 형식으로 되돌려야 한다(`events.jsonl` 원본은 이번 실행 한 번 분량만 볼륨에 남아 있다).
